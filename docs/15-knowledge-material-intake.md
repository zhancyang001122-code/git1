# 小智知识库材料准备清单

## 1. 当前真实状态

截至 2026-08-12，仓库里只有明确标注的 Demo 知识样例，用于验证检索、引用、审核和回滚流程。用户尚未提供真实客服话术、企业制度或业务政策，因此：

- 当前 RAG 没有接入用户自己的知识材料。
- 当前知识回答不能描述为“来自你的资料”。
- 千问、1024 维 Embedding、Supabase pgvector 和混合检索已经在线验证；但真实材料尚未提供，因此也没有正式知识索引或正式内容评测结论。
- 对没有资料支持的问题，正确行为是拒绝确定性回答或记录知识缺口，而不是由模型补造规则。

## 2. 第一批最小材料

不需要一次准备很多。第一批建议提供 4–8 份材料，每份只讲一个主题：

| 优先级 | 领域      | 建议材料                                       | 需要回答的典型问题                     |
| ------ | --------- | ---------------------------------------------- | -------------------------------------- |
| P0     | platform  | 产品能力边界、人工客服入口、隐私与账号处理说明 | 哪些能力是真实的？什么时候必须转人工？ |
| P0     | housing   | 历史房源数据说明、可用筛选字段、时效和免责边界 | 房源是哪一年的？能否判断当前可租？     |
| P0     | group_buy | 团购退款、核销、过期和例外规则                 | 未核销能否退？已核销怎么办？           |
| P0     | market    | 配送范围、预计送达、缺货和售后规则             | 超时怎么办？库存是否实时？             |
| P1     | housing   | 押金、退租、验房、维修责任                     | 押金何时退？验房扣款需要哪些证据？     |
| P1     | platform  | 数据保存、删除、授权和投诉处理流程             | 如何删除个人信息？如何撤回授权？       |

如果团购和超市始终是模拟业务，可以编写“作品集演示规则”，但文件标题、正文和界面必须明确写“虚构演示规则”，不能冒充真实商家制度或用户上传材料。

## 3. 每份材料必须带的元数据

系统现有数据契约需要以下字段：

- `title`：材料标题。
- `domain`：`housing`、`group_buy`、`market`、`platform` 四选一。
- `category`：主题标识，例如 `refund`、`deposit`、`delivery`、`privacy`。
- `owner_name`：谁对内容负责，例如“产品负责人”或具体部门。
- `city`：杭州、绍兴或全国；不适用时可留空。
- `version_label`：例如 `v1.0`、`2026-08`。
- `source_reference`：原始文件名、制度编号、公开网页或内部来源说明。
- `effective_from`：生效日期；未知必须明确写“待确认”，不能猜。
- `effective_until`：失效日期；长期有效可留空。
- `change_summary`：本版本相对上一版改了什么。

缺少负责人、来源或生效日期的材料可以先进入草稿，但不应直接发布为可引用知识。

## 4. 推荐的正文结构

尽量让一份文件只解决一个政策主题，并使用清楚的标题：

```markdown
# 标题

## 适用范围

适用于谁、什么地区、什么商品或订单状态。

## 核心规则

明确条件、结论和时间限制。

## 不适用与例外

哪些情况不能套用本规则。

## 办理流程

用户需要提供什么、经过哪些步骤、由谁处理。

## 转人工条件

冲突、缺资料、高风险或超权限时如何处理。

## 示例

给出一两个正例和反例。
```

Word、PDF、Excel、Markdown、TXT 都可以先发。Markdown/TXT 最容易处理；扫描 PDF 和截图需要 OCR，错误率更高。不要为了“适合 AI”自行删掉例外条款或表格列。

## 5. 不能直接进入知识库的内容

- 客户姓名、手机号、身份证号、精确住址、聊天记录等个人信息。
- API Key、Cookie、Token、数据库密码和内部登录方式。
- 未确认授权公开或再分发的第三方付费资料。
- 已过期但没有标明失效日期的制度。
- 模型生成但未经负责人核对的答案。
- 把“忽略系统规则”“调用额外工具”等指令混在资料正文中的内容。

收到材料后应先做清单、脱敏、重复与冲突检查，再进入草稿审核，不会直接发布。

## 6. 还需要一组验收问题

只有材料没有评测题，无法证明 RAG 可靠。第一批至少准备 20–30 个问题：

- 正常命中题：答案能在指定材料中找到。
- 条件组合题：同时包含地区、状态、日期或金额限制。
- 例外题：验证系统不会只引用主规则而遗漏例外。
- 无答案题：正确结果应当是拒答或转人工。
- 过期/冲突题：验证只引用当前有效版本。

每题最好附：期望结论、必须引用的材料、禁止出现的错误结论。如果你不会写，可以只提供真实用户常问问题，我再帮助整理成评测集，但答案仍需要材料负责人确认。

## 7. 交付方式

可以直接把原始文件发给我，不需要先改格式。仓库里的 `knowledge-input/` 是本机临时暂存区，默认忽略其中的真实材料，避免误提交 GitHub。收到文件后先输出“材料清单与缺口”，你确认后再进行清洗、切片、入库和评测。
