# 零基础学习与面试路线

## 1. 先校正目标

当前日期是 2026-08-13。若目标是 9 月前形成作品集，最现实的组合不是三个同等深度的“生产级项目”，而是：

1. **主项目：小智**——做深，能够运行、演示、解释架构和拿出测试证据。
2. **案例项目：方案出图 AI 全流程**——先完成聚焦单一流程的可演示版本。
3. **案例项目：企业知识助手**——先完成一个明确业务场景的 POC，不同时连接飞书、CRM 和 ERP。

三个项目都铺得很大，会得到三个看起来完整、实际经不起追问的 Demo。面试更看重能否讲清需求、取舍、数据边界、失败处理和验证证据。因此 8 月先把小智作为主项目完成并学懂，另外两个项目只做可控范围。

## 3. 每节课的固定方式

零基础不适合先背概念。每节课固定走五步：

1. **看结果**：先在页面或测试里看到输入和输出。
2. **讲概念**：只解释本节必须知道的 1 至 2 个概念。
3. **找代码**：定位这个结果经过的关键文件，不通读整个仓库。
4. **做小实验**：修改一个安全、可恢复的小点，再运行测试观察变化。
5. **面试复述**：用 30 至 60 秒说明“为什么这样设计、怎么验证”。

学习目标不是徒手重写所有代码，而是能做到：看懂数据流、判断 AI 生成代码是否可信、定位问题、说明取舍并提供证据。

## 4. 8 月执行安排

按每天至少 6 小时设计。每天建议分成：2 小时理解、2 小时跟做、1.5 小时测试与排错、0.5 小时口述复盘。连续学习 50 分钟后休息 10 分钟。

### 第一阶段：看懂一条真实链路（8 月 11 日至 14 日）

#### 第 1 课：前端、后端和 API

- 看结果：从小智页面发送一条房源问题。
- 找代码：
  - 页面交互：`web/src/components/chat/chat-experience.tsx`
  - HTTP 入口：`web/src/app/api/chat/route.ts`
  - 请求处理：`web/src/features/agent/chat-handler.ts`
- 必懂概念：浏览器是前端；服务器是后端；API 是双方约定的通信入口。
- 小实验：提交一个非法请求，观察后端返回统一错误而不是崩溃。
- 面试答案：解释为什么密钥和数据库查询不能直接放进浏览器。

#### 第 2 课：Agent 为什么要调用工具

- 看结果：打开调试面板，观察问题触发房源工具及结果卡片。
- 找代码：
  - 编排：`web/src/features/agent/orchestrator.ts`
  - 工具循环：`web/src/features/agent/tool-loop.ts`
  - 工具注册：`web/src/features/agent/tools/registry.ts`
  - 工具执行：`web/src/features/agent/tools/executor.ts`
- 必懂概念：模型负责判断意图和组织语言；价格、状态、距离等事实必须来自工具。
- 小实验：给工具传一个不合规参数，观察它被拒绝。
- 面试答案：解释“Agent 不是让模型任意执行代码，而是在白名单工具和参数契约内工作”。

#### 第 3 课：房源真实数据怎样接入

- 看结果：启动本机房源服务后查询武林广场附近历史房源。
- 找代码：
  - Python API：`services/housing-api/app/`
  - Web Adapter：`web/src/features/housing/http-adapter.ts`
  - 运行时选择：`web/src/features/housing/runtime.ts`
- 必懂概念：Adapter 把不同外部系统翻译成应用内部统一格式；只读连接防止作品误改源数据。
- 小实验：停止房源服务，观察前端如何明确降级，而不是伪造结果。
- 面试答案：说明数据日期、坐标距离、字段白名单和只读边界。

#### 第 4 课：测试是证据，不是装饰

- 看结果：运行一个单元测试和一个浏览器 E2E 测试。
- 找代码：`web/src/features/housing/__tests__/`、`web/e2e/`、`services/housing-api/tests/`。
- 必懂概念：单元测试验证小模块；契约测试验证输入输出；E2E 验证用户完整路径。
- 小实验：先故意改变一个期望值看测试失败，再恢复并确认通过。
- 面试答案：不要说“我测过了”，要说测试覆盖了什么风险以及结果是什么。

### 第二阶段：理解岗位常问的工程概念（8 月 15 日至 18 日）

#### 第 5 课：Zod、Pydantic 和参数校验

把校验理解为“门卫”：外部输入默认不可信，符合形状、类型、范围和白名单后才能进入业务逻辑。TypeScript 类型只在开发时帮助检查，Zod 会在程序运行时检查；Python 服务使用 Pydantic 承担相同职责。

验收：能指出聊天请求、工具参数和房源 API 响应分别在哪里校验，并解释为什么不能只相信模型返回的 JSON。

#### 第 6 课：超时、重试和错误归一化

- **超时**：外部服务迟迟不回应时主动停止，避免整个页面一直等待。
- **重试**：只对短暂且可恢复的失败做有限次数重试；参数错误不能靠重试解决。
- **错误归一化**：高德、千问、房源 API 的错误格式不同，进入应用后转换成稳定的 `code`、`message`、`retryable`。
- **熔断**：某服务连续失败时短时间停止继续请求，保护系统和用户体验。

验收：能演示一次服务停止或超时，并说明用户看到什么、日志记录什么、系统没有伪造什么。

#### 第 7 课：Supabase、PostgreSQL 和 RLS

- PostgreSQL 是数据库，Supabase 在它之上提供 API、登录、存储等能力。
- RLS 是数据库行级权限：即使请求到达数据库，也只允许当前用户读取或修改符合规则的记录。
- Service Role 能绕过 RLS，只能在可信服务端使用，绝不能暴露给浏览器。

远端项目已经连接，迁移和 RLS 也有真实验证证据；学习时仍要亲自看一次策略和测试，不能只背“已接通”。验收：能解释“前端隐藏按钮”为什么不是权限控制，以及 RLS 保护的最后一道边界是什么。

#### 第 8 课：稳定工具返回结构和可观测性

所有工具都返回统一成功或失败形状，包含来源、结果数和安全错误码。这样 UI、日志、测试和模型不必分别猜测每个服务的返回格式。审计只记录工具名、参数摘要、耗时、来源、结果数和错误码，不记录密钥、完整 Prompt 或完整隐私数据。

验收：选择一次成功和一次失败调用，对照页面进度、结果卡和调试信息说明它们如何对应。

### 第三阶段：理解 RAG 与知识治理（8 月 19 日至 21 日）

#### 第 9 课：RAG 到底是什么

RAG 不是模型已经“学会”你的资料，而是回答前先检索相关材料，再让模型依据检索证据回答。基本链路是：原始资料 → 文章 → 版本 → 切片 → Embedding → 检索与重排 → 带引用回答。

当前项目已有作品集首方公开资料，可以沿真实 Production 链路学习检索、引用和拒答；企业客服或制度资料仍未提供。后续企业材料及整理格式见 `docs/15-knowledge-material-intake.md`。

#### 第 10 课：为什么知识要有版本和人工审核

客服规则可能过期或互相冲突。候选知识不能自动上线，必须经过证据补充、人工审核、发布、重新索引和回归评测。回答引用需要包含来源、版本、生效日期和切片标识，以便追溯。

验收：能够解释候选 → 审核 → 原子发布与入队 → Worker 索引 → 评测流程。Demo 模式使用内存仓库；Production Live 使用 Supabase 持久化，二者必须明确区分。

#### 第 11 课：RAG 评测

至少区分两类问题：检索有没有找到正确资料，以及最终回答有没有忠于资料。没有评测集就不能仅凭“看起来回答不错”判断 RAG 已经可用。

验收：先读懂现有 20 个首方固定用例为什么包含命中题、拒答题和生成题；拿到企业资料后必须建立独立评测集，不能复用首方结果冒充客户内容质量。

### 第四阶段：外部接入与面试收口（8 月 22 日至 31 日）

Supabase、高德、千问、Embedding、`qwen3-rerank`、作品集首方 RAG、固定演示码 Auth、Production 双入口和 Vercel GitHub 自动部署已完成在线接入；当前外部收口重点是经授权的企业知识材料。企业材料必须先确定来源、负责人和生效日期，再索引和评测，不能先生成一批看似完整的客服规则冒充真实材料。

每接一个服务都必须完成：配置检查、最小在线 smoke test、错误降级、日志脱敏、契约测试、E2E、文档和面试口述。现有在线能力已经留下 Production 回归证据；缺少企业材料和真实用户测试的部分继续明确记录为待接入，不能为了“完成”伪造结果。

最后三天用于：

1. 录制 3 分钟主演示和 8 至 10 分钟技术讲解。
2. 用 `qa/demo-script.md` 演练，随机打断并追问数据来源、失败处理和安全边界。
3. 逐项核对 `qa/interview-checklist.md` 和验收标准。
4. 只在真实部署、迁移、在线 smoke test 和完整质量门全部通过后创建发布标签。

## 5. 第一条必须真正掌握的数据流

```text
用户在聊天页面输入问题
  → POST /api/chat
  → chat-handler 校验请求并选择 Demo 或 Live 运行时
  → orchestrator 驱动 Provider 与工具循环
  → ToolExecutor 校验白名单参数、执行超时和记录审计
  → Housing Adapter / Business Repository / Maps / Knowledge Service
  → 统一 ToolResult
  → SSE 逐步返回进度、文本和结果卡
  → 前端渲染并明确数据来源
```

面试时至少要能从用户输入沿这条路径讲到结果卡，并指出每一层负责什么、不负责什么。

## 6. 每日完成标准

当天不是“看过文档”就算完成，至少留下四项证据：

- 能运行或复现本节结果。
- 能指出 2 至 5 个关键文件，不需要背代码。
- 完成一个小实验并让相关测试通过。
- 能不用术语堆砌，在 60 秒内解释设计理由和真实边界。

如果只能复述概念但不能演示，说明还没有掌握；如果只能让 AI 改代码但说不出风险和验证方式，也还不能作为面试能力。

## 7. 现在从哪里开始

仍从第 1 课开始，但直接使用当前 Production Live 观察真实链路。亲自发出一条“历史房源 + 高德”问题，然后依次打开聊天组件、API 入口和请求处理文件，画出“浏览器 → API → 工具 → 数据 → 页面”的五格流程。先学懂链路，再进入第 2 课；不要因为外部服务已经接通就跳过基础概念。
