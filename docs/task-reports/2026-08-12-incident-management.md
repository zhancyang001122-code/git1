# AI Ops 事故认领闭环

## 目标

把只读阈值状态升级为可审计的站内响应流程，同时不假装已经接入短信、飞书、PagerDuty 或真实值班团队。

## 生命周期

```text
阈值超限 → open → acknowledged → resolved
                         ↘ 信号恢复自动 resolved
```

- 同一 `alert_key` 最多一个 `open/acknowledged` 事故。
- 重复监控只刷新指标和 `last_seen_at`，不重复开单。
- `open` 必须先认领，服务端拒绝跳过责任归属直接解决。
- 手动解决必须填写处理说明。
- 已解决事故不能回退到处理中；信号再次超限时创建新事故。
- 每次打开、认领、手动解决和自动恢复都追加不可变事件。

## 权限与隐私

- 两张表均启用 RLS，没有客户端策略。
- 事故主表只授权 `service_role` 读、插入和更新。
- 事件表只授权 `service_role` 读和追加，不允许更新或删除。
- Cron Route 使用 `CRON_SECRET`；管理写操作使用 HttpOnly 管理 Cookie 或 Bearer Token，Cookie 写操作强制 Same-Origin。
- 事故只保存阈值元数据和 500 字以内处理说明，不复制工具输入、输出、对话、Prompt、Cookie、IP 或凭证。

## UI

- 受保护知识运营页展示活跃事故数量、指标、状态、认领人和事件数量。
- 认领备注可选；解决说明必填，按钮在空说明时禁用。
- 使用项目现有 Token、44px 最小触控区、语义化标签和 `aria-live` Toast。

## 诚实边界

当前是“集中安全日志 + 站内事故闭环”。外部通知接收人和值班升级仍需真实团队与长期平台选择，因此验收清单继续保留“完整主动告警平台”为未完成。

- 本地应用门禁：ESLint、TypeScript、488 个 Vitest、生产构建全部通过。
- 本地数据库：8 个 pgTAP 文件共 176 项通过；事故专项 36 项同时在 linked Supabase 通过并回滚测试数据。
- 浏览器回归：48 项通过，2 项依赖独立本地真实服务的用例按配置跳过，无失败。
- 远端边界：匿名密钥不能读取事故表、事件表，也不能执行查询或同步 RPC；服务端密钥可同步和读取安全字段。
