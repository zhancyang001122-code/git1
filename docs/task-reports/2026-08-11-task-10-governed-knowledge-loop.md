# Task 10 — 受控知识演进闭环

## 完成范围

- 对话低置信、无结果和用户点踩可生成去重知识候选；候选只保存规范化问题、原因和证据 ID，不保存完整对话。
- 聊天点赞/点踩与反馈页都调用服务端 `/api/feedback`，Demo 消息先完成会话与消息归属校验。
- 新增受保护的知识运营登录、候选列表和候选详情页；管理口令换取签名 HttpOnly Cookie，不进入 URL 或客户端脚本。
- 草稿批准前强制校验标题、正文、来源、负责人、Domain、Category 和生效日期；驳回必须填写原因。
- 发布按“创建版本 → 发布 → 索引 → 评测”顺序执行，并分别展示发布、索引、评测和可检索状态。
- 索引失败时不宣称可检索；评测失败或评测服务异常时保留风险状态。只有存在上一版本时才开放回滚，首次发布不会虚假显示可回滚。
- Demo 评测实际执行四项确定性断言：索引可用、引用来源完整、发布状态正确、已驳回候选未进入索引；不再写死为 4/4。
- E2E 覆盖首次询问无依据、形成候选、人工批准、发布索引、第二次询问出现新引用，以及驳回候选不作为引用出现。

## 真实状态

- 当前仍是明确标注的 Demo 模式，知识候选、反馈、审核、发布和索引仅保存在当前 Node.js 进程内，重启后重置。
- 当前没有调用千问、百炼 Embedding/Rerank，也没有写入远程 Supabase。
- 当前演示知识是虚构资料，不是企业客服话术、合同、制度或用户上传材料。
- Live 知识运营运行时保持关闭并返回明确的未配置错误；必须在提供真实资料、Supabase 项目和模型配置后再接通。

## 后续接入所需材料

1. 可公开或已脱敏的客服 FAQ、退款/预约/配送规则、服务边界与人工转接条件。
2. 每份资料的来源名称、负责人、版本号、生效日期、失效日期和适用业务范围。
3. 冲突规则的优先级，以及哪些问题必须拒答或转人工。
4. 至少 20 组真实问法与期望答案，用于建立 RAG 评测集；需要同时包含应回答、应拒答和无答案样例。
5. 接入阶段再提供 Supabase、百炼和高德的服务端配置；密钥不写入仓库或聊天正文。
