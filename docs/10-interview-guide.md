# 面试问答指南

## 为什么不是完整美团？

我保留完整产品形态和业务链路，但开发重点是 AI 与业务系统的连接。支付、核销、履约是明确标注的模拟流程；工具契约、Adapter、RAG 版本治理、编排、测试和知识闭环是实际代码。Production 已接通 Supabase、千问、高德和 2024-11 历史房源；四份作品集首方公开资料也已完成真实 RAG 评测。企业客服知识材料仍未提供，因此不能把演示政策说成真实企业规则。

## 为什么 Supabase，不用 MySQL？

我把 Supabase 选作目标后端，因为它基于 PostgreSQL，同时提供 API、Auth、RLS 和 pgvector，适合快速交付。远端项目已应用迁移并承载 60,202 条历史房源、对话、工具审计和反馈；用户偏好还通过本地 SQL Role、PostgREST 和真实 OTP 会话验证了 RLS。企业已有 MySQL 时不会强迫迁库，而是通过 Business Service 接入。

## 为什么业务数据不用 RAG？

价格、库存、状态和筛选要精确。RAG 是相似检索，可能召回语义相关但条件不满足的数据，所以业务事实查数据库，长文本规则查知识库。

## RAG 为什么仍在 Supabase？

独立首先是职责和接口独立。Knowledge Service 已实现文章、版本、切片、混合检索和评测边界；发布与索引通过 Supabase 持久化队列解耦，独立 Worker 使用租约、`SKIP LOCKED`、幂等键和退避重试生成 Embedding。四份作品集首方公开资料已在线完成索引与检索，固定评测 20/20 通过，其中 3/3 千问自然问法用例通过强制取证、事实、版本、首方来源和引用范围检查；引用通过 `materialKind=portfolio_first_party` 与 Demo 政策区分。当前缺的是经授权的企业客服或制度资料，不是代码表结构。未来换专用搜索平台时，`search_knowledge` 不变。

## Function Calling 和 MCP？

Function Calling 是应用把工具给模型并执行函数；MCP 是标准化地向多个 AI 客户端提供工具、资源和 Prompt。当前单一 Web 客服用 Function Calling；多 Agent/多客户端时增加 MCP Adapter。

## Agent 如何路由？

通过清晰互斥的工具描述、严格 JSON Schema、系统指令、参数校验、最大轮数和评测共同实现。模型返回工具名和参数，服务端验证执行，不是完全不可控的“自动魔法”。

## Agentic RAG 如何体现？

复杂问题会识别领域、改写查询、过滤版本、混合召回、重排、判断证据是否足够，并继续调用业务和地图工具。简单问题不必都走复杂 Agent 流程。

## 为什么千问？

面向中国内地，百炼提供 OpenAI 兼容接口、Function Calling 和中文能力。Production 已验证流式多轮、项目工具调用和 1024 维 `text-embedding-v4`；代码通过 AIProvider 隔离，未来可增加其他模型。`qwen3-rerank` 仍需业务空间专属地址，当前没有假装启用。

## 如何避免过期政策？

文章和版本分离，只有 published 且有效的版本进入检索。回答引用版本；新版本发布后重建索引，旧版本归档保留审计。

## 客服如何进化？

不是每次对话自动训练。系统从无结果、低置信、点踩、重复追问和人工纠正发现缺口，生成候选，经人工审核后发布、向量化和回归评测。

## 如何评测 RAG？

检索看 Recall@5、MRR、版本命中；生成看引用正确、忠实度、相关性、拒答。知识、Prompt、模型和参数变化都跑固定回归集。

## 如何防编造？

事实必须来自工具，结构化卡片直接使用工具 JSON。工具失败时显示失败或无结果，不能让模型补值。

## 多轮上下文如何控成本？

最近消息 + 历史摘要。长期偏好按需读取，不每次注入全部数据。工具结果只保留后续必要摘要。

## 模型成本怎么估算，为什么不直接看总 Token？

`qwen-plus` 的公开价格按单次请求输入长度分档，不能把 7 天总 Token 全套最低价。service-role 专用 RPC 只聚合每次请求的模型名、输入 Token、输出 Token 和次数，不读取正文；应用逐桶选择价格档位，并显示覆盖率、价格来源与核验日。免费额度、优惠、Embedding 和 Rerank 未纳入，所以它是工程估算，不是账单。

## 可观测性做到什么程度？

工具审计和全部 API Route 的安全元数据都写入 Supabase，因此来自不同 Vercel 实例的记录可以集中查询，并通过同一个 `requestId` 关联一次请求。Route 日志只保存静态路由键、方法、状态、耗时和稳定错误码，不保存查询参数、正文、Cookie、Token、IP、响应正文或异常详情。管理页会计算工具失败率、RAG 零结果率、索引积压、RAG 评测失败率、服务端首 Token P95 和带价格版本的单会话成本估算，样本或计价覆盖不足不会显示成“正常”；Cron 把超阈值信号持久化为事故，支持认领、解决、自动恢复和不可变事件审计。当前仍缺外部通知和真实 On-call 升级，所以我会称它为“集中安全日志 + 站内事故闭环”，不会称为完整 Sentry/PagerDuty 体系。

## 为什么不用 Dify？

Dify 适合快速验证；本作品需要展示工具契约、数据边界、版本、日志和评测，所以使用可控代码。真实交付会根据客户能力选择低代码或代码框架。

## 为什么不多 Agent？

当前单 Agent + 清晰工具足够。多 Agent 增加延迟、成本和调试复杂度，只有明确独立角色、权限或并行任务才引入。

## 企业级最先补什么？

权限、审计、评测、知识治理、隐私、限流和可观测性，不是先盲目拆微服务。

## Vercel 多实例怎样限流？

Chat、Feedback、公开知识检索、地图直连和知识评测不能依赖某一个 Node.js 进程里的 `Map`，否则请求换到另一个实例就会重新计数。Production 通过 Supabase RPC 对 `scope + HMAC 客户端摘要 + 固定窗口` 做原子 upsert，所有实例共享计数；原始 IP 不进入数据库。知识评测先鉴权再计数，未授权请求不能消耗管理员额度。计数后端异常时成本敏感接口返回 503，而不是无限放行。Demo 仍使用内存实现，OTP 则按低频单邮箱作品演示的既定边界保持简化，并明确不适用于公众注册。

## HttpOnly Cookie 是否就不用防 CSRF？

不是。HttpOnly 只防止前端脚本读取 Cookie，不能单独阻止浏览器自动携带 Cookie。本项目的管理 Cookie 使用 `Secure + SameSite=Strict`，同时对 Cookie 管理写操作执行 Same-Origin 校验；跨源请求在业务逻辑之前返回 403。Bearer Token 调用用于受信脚本，不要求浏览器 Origin。管理登录表单还在解析前限制为 4 KiB，避免用超大表单消耗服务端资源。

## 如何证明不是套壳？

现场可以展示同一问题触发千问、Supabase 历史房源和高德 POI，UI 同时出现公开工具进度、结构化卡片和真实来源；第二条链路会查询 Supabase 演示商品，并只生成待用户确认的偏好提案。知识链路可现场询问“房源数据是哪一期”，展示作品集首方资料的版本化引用；Production 固定评测可重复验证 20/20 检索与 3/3 生成用例。数据库保存脱敏工具参数、耗时、结果数和错误码。企业客户材料仍是明确缺口，不用作品集资料冒充客户交付。

## 线上真实遇到过什么故障？

第一次 Live 多工具回归发现百炼流式工具分片会用 `id: null` 和 `function.name: null` 延续前一分片，原 Schema 把合法响应误判成 `QWEN_RESPONSE_INVALID`。修复后又发现模型会编造 `demo-store-001`，以及把不存在的“食品”当精确商品分类。首方 RAG 评测还发现模型会绕过知识工具、把不同问题改写成同一笼统主题、猜测不存在的分类，并把低相关 Demo 政策一起展示为引用。我没有全面放宽校验：供应商空占位只在流式兼容层处理；商品仍使用真实枚举；需要证据的问题由应用层强制 `search_knowledge`；查询必须保留完整问题，未知分类传 `null`，只有分类过滤得到 0 条时才重试一次；引用按绝对阈值和 Top1 文章相对分数过滤。最终 Production 严格知识评测达到 20/20，Live 全链路回归再次通过。

## 为什么不直接忽略模型传错的筛选条件？

静默删除筛选会让结果看似成功但违反用户条件。更可靠的做法是：Schema 明确允许值，未知条件要求模型修复一次；仍无效就返回稳定错误并停止该工具。只有用户没有提供的可选条件才应显式传 `null`，不能由应用猜测。

## 使用 Codex 应该怎么诚实回答？

我负责需求拆解、架构、工具边界、数据模型、提示词、评测和验收，并用 Codex 加速实现；我通过测试、日志和演示用例验证生成代码，而不是只接受 AI 输出。
