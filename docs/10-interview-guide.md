# 面试问答指南

## 为什么不是完整美团？

我保留完整产品形态和业务链路，但真实开发重点是 AI 与业务系统的连接。支付、核销、履约是明确标注的模拟流程；房源查询、地图、RAG、工具编排和知识闭环是真实实现。

## 为什么 Supabase，不用 MySQL？

Supabase 底层是 PostgreSQL，同时提供 API、Auth、RLS 和 pgvector，适合快速交付。企业已有 MySQL 时不会强迫迁库，而是通过 Business Service 接入。

## 为什么业务数据不用 RAG？

价格、库存、状态和筛选要精确。RAG 是相似检索，可能召回语义相关但条件不满足的数据，所以业务事实查数据库，长文本规则查知识库。

## RAG 为什么仍在 Supabase？

独立首先是职责和接口独立。Knowledge Service 有独立文章、版本、切片、检索和评测，当前底层用 pgvector。未来换专用搜索平台时，`search_knowledge` 不变。

## Function Calling 和 MCP？

Function Calling 是应用把工具给模型并执行函数；MCP 是标准化地向多个 AI 客户端提供工具、资源和 Prompt。当前单一 Web 客服用 Function Calling；多 Agent/多客户端时增加 MCP Adapter。

## Agent 如何路由？

通过清晰互斥的工具描述、严格 JSON Schema、系统指令、参数校验、最大轮数和评测共同实现。模型返回工具名和参数，服务端验证执行，不是完全不可控的“自动魔法”。

## Agentic RAG 如何体现？

复杂问题会识别领域、改写查询、过滤版本、混合召回、重排、判断证据是否足够，并继续调用业务和地图工具。简单问题不必都走复杂 Agent 流程。

## 为什么千问？

面向中国内地，百炼提供北京地域、OpenAI 兼容接口和 Function Calling。代码通过 AIProvider 隔离，未来可增加其他模型。

## 如何避免过期政策？

文章和版本分离，只有 published 且有效的版本进入检索。回答引用版本；新版本发布后重建索引，旧版本归档保留审计。

## 客服如何进化？

不是每次对话自动训练。系统从无结果、低置信、点踩、重复追问和人工纠正发现缺口，生成候选，经人工审核后发布、向量化和回归评测。

## 如何评测 RAG？

检索看 Recall@5、MRR、版本命中；生成看引用正确、忠实度、相关性、拒答。知识、Prompt、模型和参数变化都跑固定回归集。

## 如何防编造？

事实必须来自工具，结构化卡片直接使用工具 JSON。工具失败时显示失败或无结果，不能让模型补值。

## 多轮上下文如何控成本？

最近消息 + 历史摘要。长期偏好按需读取，不每次注入全部数据。工具结果只保留后续必要摘要。

## 为什么不用 Dify？

Dify 适合快速验证；本作品需要展示工具契约、数据边界、版本、日志和评测，所以使用可控代码。真实交付会根据客户能力选择低代码或代码框架。

## 为什么不多 Agent？

当前单 Agent + 清晰工具足够。多 Agent 增加延迟、成本和调试复杂度，只有明确独立角色、权限或并行任务才引入。

## 企业级最先补什么？

权限、审计、评测、知识治理、隐私、限流和可观测性，不是先盲目拆微服务。

## 如何证明不是套壳？

现场展示同一问题触发 Supabase、高德、Knowledge 三类工具；修改 Supabase 后页面和 AI 同步变化；发布新知识并重新评测。

## 使用 Codex 应该怎么诚实回答？

我负责需求拆解、架构、工具边界、数据模型、提示词、评测和验收，并用 Codex 加速实现；我通过测试、日志和演示用例验证生成代码，而不是只接受 AI 输出。
